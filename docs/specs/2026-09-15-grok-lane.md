# grok lane — grok-4.6 for explore, implement, and review

## Goal

Add a `grok` engine, mirroring the existing `claude` engine, so explore and
implement can run on `grok-4.6` via the local `grok` CLI. Unlike `claude`, grok
IS allowed on the review lane: it is a different model family from every codex
profile, which is exactly what the isolated review wants. The reviewer subagent
learns it as a second-opinion option.

## Ground truth (verified live, not assumed)

- `grok 1.0.30`, binary `~/.grok/bin/grok`, already on PATH, logged in.
- `grok models` → `grok-4.6` (default), `grok-4.5`.
- `--reasoning-effort` accepts **xhigh | high | medium | low**. There is no
  `max`; passing it exits non-zero with a usage error. codex-run's default
  `EFFORT=max` must therefore be translated, never forwarded.
- Headless: `grok -p "<prompt>" --model grok-4.6 --output-format plain` prints
  the answer to stdout and exits 0.
- `--disallowed-tools` takes a **comma-separated list of grok's own tool names**.
  The edit tools are `write` and `search_replace`; unknown names (`Edit`,
  `Write`) are silently ignored, so the claude lane's list would be a no-op.
- `--cwd DIR` sets the working directory; `--no-subagents` disables subagent
  spawning; `--permission-mode bypassPermissions` auto-approves tools.

## Known ceiling

`--disallowed-tools write,search_replace` removes the edit tools but
`run_terminal_command` can still write, so a read-only grok lane is weaker
isolation than codex's `-s read-only` sandbox — the same ceiling the claude lane
carries. Mark it with a `ponytail:` comment naming the ceiling. Do not build a
sandbox for it. This applies to the review lane too: the isolation that matters
there is that the box holds only `plan.md` and `changes.diff`.
